# Daily Automation — Design Spec (2026-06-12)

## Goal

The board refreshes itself: a scheduled robot (GitHub Actions) updates player stats each morning, recomputes today's slate through the day as lineups/weather/scratches arrive, freezes each game's numbers at first pitch, rolls the 7-day window, and republishes the locked Vercel site — with zero manual steps and zero monthly cost.

## User decisions (2026-06-12)

| Decision | Choice |
|---|---|
| Where the robot runs | **GitHub Actions, free tier** (private repo, 2,000 min/month budget) |
| How data reaches the site | **Robot deploys to Vercel directly** via CLI + token; generated data is never committed to git |
| Refresh cadence | **Hourly 10am–11pm ET, plus :30 extras 3–7pm ET** (lineup rush window) |
| Morning run | **6:00 AM ET** (yesterday's Statcast is finalized overnight; board is live by breakfast) |
| Site unlock | NOT part of this build — user decides manually after automation proves itself |

## Schedule (cron, UTC — assumes EDT; MLB season sits almost entirely inside daylight time, ±1h drift at season edges is acceptable)

| Job | ET | UTC cron |
|---|---|---|
| Morning | 6:00 AM | `0 10 * * *` |
| Hourly refresh | 10am–11pm | `0 14-23 * * *` and `0 0-3 * * *` |
| Rush extras | 3:30/4:30/5:30/6:30 PM | `30 19-22 * * *` |

Both workflows also expose `workflow_dispatch` (a manual "Run now" button) — that is how we test before enabling cron.

"Today" inside any job = the **current date in America/New_York**, not UTC (a 1 AM UTC run still belongs to the previous ET day).

## Architecture

Two thin GitHub workflow files; all real logic lives in tested Python entrypoints.

```
.github/workflows/morning.yml   -> python -m model.jobs morning
.github/workflows/refresh.yml   -> python -m model.jobs refresh
```

Each workflow: checkout → set up Python + pip cache → restore `.cache/` (actions/cache, keyed by ET date with fallback to the newest previous key) → run the job → if the job reports "changed", deploy: `npx vercel deploy --prod --cwd web --token=$VERCEL_TOKEN`. Concurrency group `refresh` with queueing so runs never overlap.

### New module: `model/daily.py` (pure logic, unit-tested)

1. **`merge_day_into_caches(day_rows, cache_dir)` — incremental stats.**
   One league-wide Statcast pull for a single date (`fetch.statcast_day(date)`, slim columns: `batter, pitcher, game_date, events, launch_speed, game_pk`) is split per player and appended to the existing `bat-events-*` / `pit-events-*` cache files. Idempotent: rows for that `game_date` are dropped before appending, so re-running a day never duplicates. Handles multi-day gaps (morning job walks every missing date since the cache's newest game_date, capped at 10 days; beyond that it falls back to a full per-player re-pull). This replaces the "clear cache, re-download 500 players" approach: morning run drops from ~45 min to ~8 min.

2. **`refresh_today(date_str)` — freeze-merge compute.**
   - Load the existing `web/public/data/<date>.json` if present.
   - Fetch today's schedule. For games **already started**: carry their HR rows, K rows, and games entries over from the existing file **unchanged** (frozen at the last pre-game compute). Never recompute, never drop.
   - For games not started: compute fresh via the existing `make_profile_fns`/`build_*` plumbing.
   - Concatenate, re-sort, write `<date>.json` + mirror `latest.json` + `_update_index` (rolling-7 + prune already built).
   - Postponed/cancelled games that vanish from the schedule: keep their frozen rows if they had started, drop if they never did.
   - Returns `changed: bool` — whether the output file's content hash actually changed (drives deploy-skip).
   - **History integrity rule:** a date file is only ever touched on its own ET day. Past days are never regenerated by automation — each file is the honest pre-game record (required for the future public pick-log). `model/backfill.py` remains a manual/dev tool only.

3. **Early-exit signature.** Before computing, `refresh` builds a structural signature of today: per game — probable/actual pitcher ids, lineup player ids, started flag. If the signature equals the one saved from the last run (`.cache/last-signature.json`) AND the last publish was < 90 minutes ago, exit without computing (weather-only drift doesn't merit a republish that often). The morning job never early-exits.

### `model/jobs.py` (thin orchestrators)

- `morning`: refresh BvP pairs (delete `bvp-*` cache files — career head-to-head moves daily for pairs that faced off; ~150 cheap re-pulls), run incremental stats update, then `refresh_today` (no early-exit), report changed.
- `refresh`: early-exit check, then `refresh_today`, report changed.
- Exit code nonzero on failure → GitHub's default failure email to the repo owner is the alert channel. A failed run leaves the site untouched on its last good board.

### Engine hardening (benefits manual runs too)

- Retry-with-backoff (3 attempts) on Open-Meteo and Statcast calls inside `fetch` — addresses the observed rate-limit/timeout flakiness (2026-06-11/12).

## Secrets (GitHub repo → Settings → Secrets)

- `VERCEL_TOKEN` — user creates at vercel.com → Account Settings → Tokens (walk-through during implementation).
- `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` — copied from the existing local `web/.vercel/project.json`.

## Budget check (free-tier fit)

Morning ~8 min + 18 intraday runs of which many early-exit (~0.5–1 min) and the rest ~3 min ≈ **50–60 min/day ≈ 1,500–1,800/month** vs 2,000 free. Vercel deploys ≤ 19/day vs 100/day limit. Headroom on both. Cadence is one cron line to adjust later.

## Error handling summary

| Failure | Behavior |
|---|---|
| Statcast/weather flaky | In-engine retries; if still failing, job fails → email; site keeps last good board |
| One game's lineup fetch fails | That game computes without lineups (existing graceful paths); rest of slate unaffected |
| Run overlaps next schedule | Concurrency queue — never two writers |
| Deploy fails after compute | Job fails → email; next run recomputes and redeploys (idempotent) |
| Cache lost/evicted | Multi-day gap walker rebuilds incrementally; worst case full re-pull path (slow but automatic) |

## Testing

- Unit (no network): `merge_day_into_caches` dedupe/append/gap behavior; `refresh_today` freeze-merge (started rows carried byte-identical, non-started recomputed, vanished-game rules); signature compare/early-exit decision.
- Live: `workflow_dispatch` manual runs observed end-to-end (compute → deploy → site shows new stamp) before any cron is enabled.

## Rollout

1. Build + unit-test everything locally; run `python -m model.jobs refresh` by hand.
2. Add secrets with the user; trigger `workflow_dispatch` runs; verify the locked site updates.
3. Enable crons; observe for 2–3 days (user spot-checks the board + updated stamp).
4. User decides separately when to unlock the site to the public.

## Out of scope

Site unlock; pick-log/grader; swingman starts-vs-appearances and other model roadmap items; prior-season blending for April; Vercel Blob storage (revisit only if deploy-per-refresh ever becomes a constraint).
